本文回答一个问题：**把本项目重构成 Rust 后端加 Flutter 界面之后，现有的每一项功能能不能保持，或者做得更好。**

## 1. 结论

**功能可以完整保持，并且有多处明确可以做得更好。** 全部核对项里只有 1 项存在行为差异，已决定交给 Flutter 原生实现、不做补偿；另有一处默认配置必须主动关闭。

| 核对区域 | 保持 | 优化 | 退化 |
|---|---|---|---|
| 反墙网络层（[01-net-layer.md](01-net-layer.md)） | 5 项 | 2 项 | 0 |
| 图片子系统（[06-image-parity.md](06-image-parity.md)，12 项） | 8 项 | 4 项 | 0 |
| 交互与界面（[07-interaction-parity.md](07-interaction-parity.md)，18 项） | 14 项 | 3 项 | 1 项（见 [§4](#4-触控板翻页的处理决定)） |
| 其余功能域（推荐、搜索、小说、下载、收藏等，[§2.4](#24-其余功能域)） | 全部 | — | 0 |

三个区域之间有个别项目重复出现（Keychain、Ugoira 播放、浏览器打开），因此不给总计数字。唯一存在行为差异的 `FeedPager` 触控板翻页改为使用 Flutter 原生滚动物理，见 [§4](#4-触控板翻页的处理决定)。需要主动关闭的默认配置是应用沙盒（App Sandbox），见 [§5](#5-必须主动关闭的默认配置应用沙盒)。

技术前提已经实测通过：**Rust 可以做到 TLS 握手时不发送 SNI**（服务器名称指示），ClientHello 字节层面验证无该扩展，真实 CDN 端到端拿到 HTTP 200，同一 IP 发送 SNI 则被连接重置。这是绕过 GFW 的核心手段，见 [01-net-layer.md](01-net-layer.md)。

## 2. 功能对等总表

### 2.1 反墙网络层

| 现有功能 | 判定 | 依据 |
|---|---|---|
| QUIC（快速 UDP 网络连接）直连 API | 保持 | `quinn` + `h3`，已实测拿到 HTTP/3 响应 |
| 无 SNI TLS 取图片 | 保持 | rustls `enable_sni = false`，已实测 |
| ECH（加密客户端问候） | 优化 | JNI 层整体删除，`rust/ech` 逻辑内联为普通函数调用 |

## 3. 判定为优化的项目

下表列出功能行为上能明确变好的项目。ECH 去掉 JNI 边界与 DoH 修复两项已在 [§2.1](#21-反墙网络层) 列出，此处不重复。

| 优化项 | 现在 | 重构后 |
|---|---|---|
| Ugoira 播放内存 | 所有帧一次性解码进内存常驻，大动图会吃数 GB | 只保留当前帧与预解码的下一帧 |
| 图片解码 | 整图解码后再缩放，2895×4091 JPEG 峰值 45.2 MB | 解码阶段直接降采样，同样图片 0.5 MB，耗时从 128ms 降到 92ms |
| 并发请求去重 | 无此机制，瀑布流快速滚动会重复下载 | 同一 URL 共享同一次下载 |
| 磁盘缓存淘汰 | 纯 LRU，实测 48 个大文件占 77% 容量，一张 17.6 MB 原图会挤掉约 400 张缩略图 | 按大小加权或缩略图与原图分池限额 |
| 反墙条件判定 | 图片客户端要判断两个条件才决定是否启用无 SNI | 按域名查表选传输策略，条件集中在一处 |
| 作品简介渲染 | 手写解析器有三个缺陷：缺少 `</a>` 闭合标签时丢弃剩余全部文本、标签交叉嵌套时样式错乱、文本逐字符追加 | 换成熟渲染库，容错解析不会丢内容 |

另外四项属于「消除现有复杂度」，功能等价但更稳：

- 触控板手势不再需要 JNA（Java 本地调用接口）直接操作 AppKit 私有结构，Flutter 引擎已经实现
- 触控板和鼠标滚轮分成两条独立事件通道，现有代码里试探「这次滚动是捏合还是滚轮」的判断可以删除
- 系统菜单项不再需要每秒重试 10 次的时序处理
- 托盘不再需要反射修改 JDK 私有静态字段

## 4. 触控板翻页的处理决定

**差异的位置**：`ui/component/FeedPager.kt` 的触控板横滑翻页，仅在「短促快甩后立刻抬手」这一场景。

**原因**：Flutter 引擎跳过触控板的惯性阶段事件，改由框架自己生成惯性（引擎源码 `FlutterViewController.mm` 注释写明 `Skip momentum update events`）。现有代码里依赖原生惯性阶段事件的那条冗余判定路径失去数据来源。

主路径不受影响：手指抬起时引擎照常送达手势结束事件，即时结算完整保留。

**决定：交给 Flutter 原生的滚动物理，不做补偿。**

`PointerPanZoom` 这套事件的设计动机就是让触控板滚动产生惯性（官方行为变更文档写明惯性取决于手指离开触控板的时机），相关手势识别器注册关注后由手势竞技场仲裁，惯性结算由 `PageScrollPhysics` 产生。因此下面这些现有代码整体删除，不移植：

- `peakHorizontalVelocity` 速度采样与 `FAST_SWIPE_VELOCITY` 判定（第 180 到 187 行、第 134 到 137 行）
- `settleHorizontalGesture` 的双条件结算（第 131 到 151 行）
- `ignoreMomentum` 与吞掉惯性事件的分支（第 157 到 161 行）

连带消失的是全局原生事件监视器的所有者令牌机制：现有监视器全局唯一，`HorizontalPager` 会预加载相邻页、每页都会注册并在销毁时清空它，因此需要用 `scrollHandlerToken` 保护。改为每个部件各自处理手势后不再需要。

**接受的行为差异**：以下三条按 Flutter 默认表现处理，真机上确认是否可接受。

| 行为 | 现有做法 |
|---|---|
| 横向双指滑动翻页，与页面内纵向列表滚动共存 | 显式轴向仲裁：位移比例 0.55 加 2 像素决策距离 |
| 短促快甩翻页 | 位移达视口宽度 12%，或速度达 1200px/s 且位移达 6% |
| 缓慢拖动未过阈值 | 回弹到原页 |

**代价**：手势竞技场按初始拖动方向裁定胜负，没有比例与决策距离这类可调参数。

**回退做法**：若默认裁定或甩动阈值不可接受，在同一个部件内加 `Listener` 接收 `onPointerPanZoomStart/Update/End` 并用分页控制器手动驱动结算。`FeedPager` 对外接口不变，影响范围限于该部件。回退时这两个常量需要按真机数据重新定值：

| 常量 | 现值 | 需要调整的原因 |
|---|---|---|
| `TRACKPAD_AXIS_DECISION_DISTANCE` | 2f | 原生的滚动位移已乘 `contentsScale` 是物理像素，Flutter 给出的位移是逻辑像素，Retina 屏幕上相差 2 倍 |
| `FAST_SWIPE_VELOCITY` | 1200f | 单位差异，加上若改用窗口平均速度必然低于单帧峰值，阈值需要下调 |

## 5. 必须主动关闭的默认配置：应用沙盒

这一项与语言或框架的能力无关，是 Flutter macOS 模板的默认配置与本项目需求冲突，必须主动处理。

**事实**（来自 Flutter 官方 macOS 构建文档）：Flutter 的 macOS 构建默认「已签名并启用应用沙盒（App Sandbox）」。文档原文指出：

- 不添加 `com.apple.security.network.client` 权限时，网络请求会直接失败并报 `Operation not permitted`
- `com.apple.security.network.server` 权限**只对调试与性能分析构建默认开启**，正式构建需要自行添加，否则「调试正常、正式版失败」

**本项目的三项需求都踩在这些默认值上**：

| 需求 | 沙盒下的后果 |
|---|---|
| 发起 HTTPS 请求（API 与图片） | 正式构建缺少 `network.client`，全部网络失败 |
| 启动本地回调服务器接收 OAuth 授权码 | 正式构建缺少 `network.server`，无法监听本地端口 |
| 把作品下载到用户选择的自定目录 | 沙盒限制写入应用容器外的路径，下载路径设置失效 |
| 读取系统钥匙串中的 token | 沙盒下钥匙串访问受权限组限制 |

**处理方式**：在两个权限声明文件中把 `com.apple.security.app-sandbox` 设为 `false`。

这条路径成立的理由：应用沙盒是上架 Mac App Store 的必需条件，而本项目的分发方式是 GitHub Releases 的 DMG（现有 `release.yml` 就是上传 DMG）。苹果的公证（notarization）要求的是加固运行时（hardened runtime），与应用沙盒无关。关闭沙盒后，网络、文件、钥匙串三方面的行为与现在未沙盒的 Compose 版本完全一致，功能对等成立。

如果将来要上架 Mac App Store，则需要保留沙盒并逐项补齐权限，同时把下载路径改为「用户通过系统文件选择器授权」并持久化访问凭据（security-scoped bookmark）。这条路线会改变下载路径设置的交互方式。

## 6. 实测结果与剩余待验项

### 6.1 骨架阶段已在云端跑通（实测数据）

`flutter build macos --release` 在 GitHub Actions 的 `macos-latest` 上跑通，五项验收全部成立：

| 验收项 | 实测结果 |
|---|---|
| 正式包可构建 | 构建成功，产出 `PixivShaft.app` |
| 目录结构与体积 | 应用包 **51 MB**：FlutterMacOS.framework 29 MB、pixiv_core.framework 12 MB、App.framework 8.8 MB；DMG **24 MB** |
| Rust 构建钩子自动触发 | 未写任何额外 Rust 步骤，钩子自行解析 `Cargo.toml` 与 `rust-toolchain.toml` 并完成编译 |
| 关闭沙盒后正式包可联网 | 正式包实跑输出 `[probe] 取回 130006 字节`，与本地核心验证同一张图片；内嵌权限声明实测为 `com.apple.security.app-sandbox` = `false` |
| 无 SNI 取回真实图片并显示 | 同上，字节数一致，界面经 `Image.memory` 显示 |

对照现有版本：应用包从 197 MB 降到 51 MB，DMG 从 131 MB 降到 24 MB。

两处与先前判断不同的实测结论：

- **Rust 产物是内嵌的动态框架，不是静态库。** `flutter_rust_bridge` 的 native-assets 钩子产出 `Contents/Frameworks/pixiv_core.framework`，通用二进制（arm64 与 x86_64），由构建流程随应用一并签名，不需要手工单独签名内层产物。
- **`rust-toolchain.toml` 必须同时列出两种架构。** `flutter build macos` 按通用二进制构建，构建钩子对 arm64 与 x86_64 各调用一次；只列 arm64 会直接抛 `RustValidationException`。

### 6.2 授权与接口层已在云端验证

| 验收项 | 实测结果 |
|---|---|
| PKCE 符合 S256 定义 | verifier 长度 43，challenge 与 `base64url(sha256(verifier))` 一致 |
| 授权地址参数完整 | 含 `client_id`、`response_type=code`、`code_challenge`、`code_challenge_method=S256` |
| 接口签名头被服务端接受 | 不带凭据调用推荐接口返回 400 并带 `Error occurred at the OAuth process` 文案，即服务端只提示缺凭据，未拒绝签名 |
| 正式包可启动 | 构建产物启动后保持存活 |

一处实测暴露的关键事实：**`app-api.pixiv.net` 走普通 HTTPS 在国内网络不通**，本机请求直接失败。这正是现有版本要用 QUIC 发 API 请求的原因，因此国内可用的 API 通路要等 QUIC 接入（第三阶段）。上面的签名头验证在不受干扰的网络上跑通。

另有一处流程改动：现有版本里的 `OAuthCallbackServer` 只有自身测试引用，是死代码。真实流程是打开系统浏览器、用户粘贴回调地址，因此新版本不起本地 HTTP 服务。

### 6.3 剩余待验项

| 项 | 验证方式 |
|---|---|
| 触控板翻页手感是否可接受 | 真机确认 [§4](#4-触控板翻页的处理决定) 列出的三条行为：横向滑动与纵向滚动共存时的裁定、短促快甩能否翻页、慢速拖动是否回弹 |
| 简介渲染库在桌面端的实际效果与链接点击 | 真机验证 |
| 日语输入法真机完整输入 | 系统日语输入法输入多段长句并逐步转换 |
| 关闭沙盒后能否开本地 OAuth 回调服务器、写入用户选择的下载目录 | 待这两条链路接入后按同样方式在正式包里实跑 |
| 签名与公证 | 见 [§7](#7-云端构建) |

日语输入法有一条硬版本约束：**Flutter 版本必须不低于 3.35.0**。低于此版本时，日语确定转换会重复后半句（[flutter/flutter#160935](https://github.com/flutter/flutter/issues/160935)，2025-06 修复）。另有一项仍开放的问题（[#190525](https://github.com/flutter/flutter/issues/190525)）：日语用回车确定转换时，回车会同时被快捷键系统收到，绑定「回车发送」的评论框每次确定都会误发送。补偿做法是在提交逻辑里判断输入法组合状态（`composing.isValid`）后再发送。

## 7. 云端构建

构建全部放在 GitHub Actions，本机不产出构建物。

**集成方式**：`native-assets`，不用 cargokit。cargokit 在当前 Flutter 上是死路（macOS 工程已切到 Swift Package Manager，没有 Podfile，而它仍生成 podspec）。native-assets 自 Flutter 3.38.0 起在正式版默认启用（[flutter/flutter#176285](https://github.com/flutter/flutter/pull/176285)），不需要额外开关。钩子文件 `hook/build.dart` 用 `FlutterRustBridgeNativeAssetsBuilder`，`cratePath` 指向 `rust/core`。

**代码生成也在云端**：`flutter_rust_bridge_codegen` 需要 `cargo expand`，而展开依赖 nightly 工具链，本机不装。生成产物提交进仓库，由工作流在接口或配置变更时重新生成，避免出现「改了 Rust 接口却忘记重新生成」的漂移。

**Flutter 版本锁死 3.47.5**，不写 `stable` 通道。理由见 [§6.3](#63-剩余待验项) 的输入法版本约束，通道漂移可能导致已修复的问题回归。


**签名与公证**：现有 DMG 既未签名也未公证（核对 `release.yml` 确认），所以这一步属于新增能力，与本次重构无关，可以单独决定是否要做。不做时构建链路不需要任何凭据；要做时需要 Apple Developer Program 会员资格与 7 项凭据。构建配置里给每一步加了条件守卫，未配置凭据时流水线不会失败。

**缓存**：Flutter 开发包与包缓存由 `subosito/flutter-action` 的缓存选项管理，Rust 依赖用 `Swatinem/rust-cache`。

**一处作废的机制**：现有 `updateEchPrebuilt` 任务迁移后没有对应物。它存在的意义是「把预编译产物提交到代码仓库，让默认构建链不跑 Rust 编译」，而 native-assets 下 Rust 编译由构建钩子直接驱动，这个机制整体作废。

## 8. 桥接层选型

推荐 **flutter_rust_bridge v2，锁定 2.13.0**。

本项目有四类持续数据流需要从后端推送到界面：下载进度、列表分页、图片字节流、评论分页。该方案把它们直接映射为 Dart 的流（`Stream`），无需手写样板。已实测代码生成跑通：用本项目真实接口形态写的异步函数与流式接口全部正确生成，无手写补丁。

性能实测：256 KB 分块字节流达到 11765 帧每秒（约 3.07 GB/s）；在 900 MB/s 持续压力下，界面帧间隔中位数 16.0 毫秒、最大 17.1 毫秒，没有可感知卡顿。后端运行时与界面隔离，300 毫秒的同步任务改为异步后调用方 319 微秒即返回。

需要留意：流式接口没有背压（backpressure），下载进度要在界面侧按 100 毫秒或每 1% 节流推送。

## 9. 分支与发布安排

迁移在独立分支上推进，`main` 在此期间保持可用的 Kotlin 版本。新版本达到功能对等后，把原 Kotlin 分支改名为 `legacy`，Rust + Flutter 版本成为 `main`。

**切换时要一并处理的几件事**：

| 项 | 处理 |
|---|---|
| 默认分支与分支保护规则 | 改名后同步指向新 `main` |
| `ci.yml` 的触发条件 | 写成 `push: branches: [main]`，在 `legacy` 上不会触发。冻结分支不需要持续构建，保持原样即可 |
| `release.yml` 的触发条件 | 按 `v*` 标签触发，与分支无关；运行的是被打标签的那个提交上的工作流定义。因此打标签时指向新 `main` 的提交即可 |
| 迁移分支的工作流 | 早期就替换掉工作流文件，否则在迁移分支上提的合并请求会去跑 Kotlin 的构建与测试 |
| 待合并的请求 | 改名之前先清掉指向旧 `main` 的未合并请求 |
| `rust/ech/prebuilt` 与 `updateEchPrebuilt` | 新版本里整体作废，见 [§7](#7-云端构建) |
| 应用标识 | 包标识与产品名沿用 `ceui.pixiv.Shaft` 与 `PixivShaft`，让新版本就地替换旧应用 |
| 钥匙串里的旧凭据 | 不迁移，用户重新登录。与「不保留向后兼容」一致 |

`legacy` 分支冻结后不再接受功能改动，只用于对照现有行为。
